## 1. Architecture summary

The E2E Lab Booking portal is an internal-only React SPA served from Amazon S3 via Amazon CloudFront. Authenticated API calls traverse Amazon API Gateway (REST or HTTP API) to AWS Lambda functions that perform booking business logic, with state persisted in Amazon DynamoDB. Identity is managed by Amazon Cognito User Pools, federated to the corporate SSO (SAML/OIDC) so that only corporate employees can authenticate. The principal trust boundaries are: (1) public internet → CloudFront edge, (2) CloudFront → API Gateway, (3) API Gateway → Lambda, and (4) Lambda → DynamoDB. Because the exposure is internal-only, all entry points should be locked to corporate-network or Cognito-authenticated traffic; no unauthenticated path should reach any data tier.

## 3. Security, privacy, availability and operational risks

- **[High] Security: Overprivileged Lambda IAM Roles** — If Lambda execution roles use wildcard actions or resources, a single exploited function can compromise the entire AWS account. This is the highest-likelihood path to account-level breach in a serverless architecture.
- **[High] Security: Horizontal Authorization Bypass in Booking API** — Application logic that trusts user-supplied identity parameters rather than Cognito JWT claims is a common OWASP API3 (Broken Object Level Authorization) vulnerability, allowing employees to access or modify others' bookings.
- **[High] Security: Malicious SPA Injection via Compromised CI/CD** — Without strict controls on who can write to the S3 origin bucket, a compromised deployment pipeline can deliver malicious JavaScript to all users, harvesting Cognito tokens or booking data.
- **[Medium] Security: Insufficient Dependency and Runtime Vulnerability Management** — Lambda functions and the React SPA bundle include third-party npm packages that may carry known CVEs; without automated scanning these can be exploited to achieve code execution or data exfiltration.
- **[Medium] Privacy: Employee Booking Data Exposure** — Booking records implicitly reveal employee work patterns and lab usage; overly broad API access or misconfigured DynamoDB permissions could expose this internal business data to unauthorized staff.
- **[Low] Privacy: Verbose Logging of Personal Identifiers** — CloudWatch Logs or API Gateway access logs may capture employee email addresses or Cognito sub IDs; log retention and access policies must align with internal data handling policies.
- **[Medium] Availability: Lambda Concurrency Exhaustion** — Without reserved concurrency limits or API throttling, a burst of legitimate or malicious requests can exhaust the account-level Lambda concurrency pool, impacting other internal workloads.
- **[Medium] Availability: DynamoDB Throttling Under Load** — A mis-configured or under-provisioned DynamoDB table will return throttling errors during peak lab booking periods (e.g., morning rush), causing booking failures and user frustration.
- **[Medium] Operational: Lack of Tamper-Evident Audit Logging** — Without structured, correlated audit logs spanning Cognito, API Gateway, Lambda, and DynamoDB, incident investigation and dispute resolution for booking conflicts become infeasible.
- **[Medium] Operational: No Formal Incident Response Runbook** — As an internal portal with corporate SSO integration, a compromised account or token could have cross-system blast radius; without a defined runbook, response time will be extended.

## 6. Security user stories and acceptance criteria

### 6.1 Secure API Authentication Enforcement

As a security engineer, I want every API Gateway route to require a valid Cognito JWT so that unauthenticated or expired sessions cannot access any booking data.

**Acceptance criteria**

- Given an unauthenticated HTTP request to any API route, when it is received by API Gateway, then the response is HTTP 401 with no booking data in the body.
- Given a request with an expired Cognito JWT, when it is sent to any API route, then the response is HTTP 401 and an error is logged to CloudWatch.
- Given a valid Cognito JWT for employee A, when employee A requests their own bookings, then the response is HTTP 200 with only employee A's records.
- Given a valid Cognito JWT for employee A, when employee A attempts to retrieve or modify employee B's bookings by supplying B's userId in the request, then the response is HTTP 403.

### 6.2 Tamper-Resistant Audit Logging

As an operations manager, I want all booking create, update, and cancel actions to be recorded in a tamper-resistant audit log so that booking disputes can be resolved authoritatively.

**Acceptance criteria**

- Given an employee creates a booking, when the Lambda function processes the request, then an audit log entry containing the Cognito sub, action type, resource ID, and UTC timestamp is written to CloudWatch Logs.
- Given a booking is cancelled, when the DynamoDB item is modified, then a CloudTrail data event records the change within 5 minutes and is stored in the Object Lock S3 bucket.
- Given an attempt to delete or overwrite CloudTrail logs, when the S3 Object Lock policy is active, then the deletion is denied and an S3 access-denied event is recorded.

### 6.3 Safe Static Asset Delivery

As a developer, I want all SPA assets to be served exclusively through CloudFront with a strict Content-Security-Policy so that injected or third-party scripts cannot execute in the user's browser.

**Acceptance criteria**

- Given a direct HTTP request to the S3 bucket origin URL, when the request is made without a valid OAC signature, then S3 returns HTTP 403 and no asset content.
- Given the browser loads the SPA, when it parses the HTTP response headers from CloudFront, then a Content-Security-Policy header with 'script-src: self' and no 'unsafe-inline' directive is present.
- Given a deployment pipeline pushes new SPA assets, when the pipeline role is the only role with S3 PutObject permission, then an attempt to upload from any other IAM principal is denied with HTTP 403.

### 6.4 Rate Limiting and Abuse Prevention

As a platform engineer, I want API Gateway throttling and Lambda reserved concurrency limits in place so that no single user or misbehaving client can degrade the booking service for others.

**Acceptance criteria**

- Given a client sends more than the configured burst limit of requests in a short window, when API Gateway evaluates the request, then the excess requests receive HTTP 429 responses.
- Given Lambda reserved concurrency is set for the booking function, when concurrent invocations exceed the limit, then additional invocations are throttled and a CloudWatch alarm fires.
- Given a CloudWatch alarm threshold for abnormal invocation rate is breached, when the alarm transitions to ALARM state, then an SNS notification is delivered to the platform team within 5 minutes.

### 6.5 Dependency Vulnerability Prevention in CI/CD

As a developer, I want the CI/CD pipeline to automatically scan Lambda and SPA dependencies for known vulnerabilities so that critical CVEs are never deployed to production.

**Acceptance criteria**

- Given a pull request introduces an npm package with a known critical CVE, when the CI pipeline runs the vulnerability scan step, then the build fails and the PR is blocked from merging.
- Given all dependencies have no critical or high CVEs, when the CI pipeline runs the vulnerability scan step, then the build proceeds normally to the deployment stage.
- Given a new CVE is published for an existing dependency after deployment, when the scheduled daily scan runs, then a ticket or alert is automatically created for the development team.
